**Model**: RandomForestClassifier, `n_estimators=200, max_depth=16, min_samples_leaf=1, class_weight=None` (`DEFAULT_MODEL_PARAMS` in `train_model.py` — walk-forward tuned via `--tune`, re-tune whenever the feature set, training-set size, OR data-quality filtering changes, since the winning config shifts each time — it's flipped `class_weight` None↔"balanced" twice across five re-tunes so far; hyperparameter search on a dataset this size (~459 rows) is itself somewhat noisy, so don't read too much into which single config "won" a given round). 14 features, **all carrying real signal**:
`season_best, career_best, pb_gap, meets_count, consistency, yoy_improvement, age, season_rank, season_percentile, weighted_season_best, wind_adj_season_best, recent_trend, days_since_last, h2h_win_rate, gap_variability` (**15**, requires `--with-recency --with-h2h --with-schedule`)

**Read Next Steps 0p before drawing conclusions from the importance ranking.** Four of those columns are measured near-duplicates (`season_best` vs `career_best`/`wind_adj_season_best` correlate **+1.000**; `season_rank` vs `season_percentile` **-0.997**), the raw marks carry ~0 pooled signal across 32 disciplines, and **removing the duplicates costs a point** — the redundancy is load-bearing under `max_features` sampling. Do not tidy it away.

**Ground truth is real, not hand-typed.** `src/dl_final_results_scraper.py` pulls actual Diamond League Final results (2018-2025, excluding 2020) directly from World Athletics' own public GraphQL API — the same API the site's own frontend uses (`x-api-key` is a public key shipped in every page load, not a secret). It finds each year's Final by filtering `rankingCategory == "DF"` and reads which disciplines were contested (and under what name — e.g. "Mile" some years instead of "1500 Metres") directly from what's present in the response, rather than a hand-maintained list. **2018/2019 were initially assumed to need a different scoring format** (the Final was split across two meetings, Zurich + Brussels) and skipped — checking the actual per-meeting data (2026-08-23) showed each of the 32 disciplines' DF group appears at exactly one of the two meetings, never both, so it's a two-city Final, not a split score. The scraper now aggregates across however many DF meetings a year has instead of assuming exactly one. 2020 (COVID-era "Inspiration Games" exhibition) is still deliberately excluded.

**Training features go beyond a season-best toplist.** `src/season_results_scraper.py` pulls every *regular-season* Diamond League meeting's results (not just the Final — that would leak the label) for 2018-2025 (excluding 2020), giving real multiple-marks-per-athlete-per-season data. This is what makes `meets_count`/`consistency`/`recent_trend` real features instead of structural zeros.

**Beyond the DL circuit: `src/major_meets_scraper.py`** (added 2026-08-23, user-requested "meets with the big athletes") adds real per-meeting results from the Olympic Games, the senior outdoor World Athletics Championships, World Athletics Continental Tour **Gold tier only** (`rankingCategory == "A"`, filtered out of a much larger Silver/Bronze/Challenger pool), and the European Athletics Championships (the other five Area Championships — African/Asian/American/Oceania/NACAC — were deliberately left out per the user, quality varies too much by continent). These groups were found via `getCalendarEvents`'s own `options.competitionGroups`/`rankingCategories` introspection, not guessed.

**Both per-meeting scrapers filter to "recognized" athletes only** (`dl_final_results_scraper.load_recognized_names`): a row is kept only if that athlete appears somewhere in the discipline's own toplist (any year, not just that exact year — deliberately lenient about single-year toplist gaps). This exists because a big meeting can still have a weak field in a discipline that isn't its main draw (e.g. a field-filler making a Continental Tour Gold meeting's javelin final) — keeping those marks would add noise (thin, one-off meets_count/consistency signal) rather than real information about the athletes DL Final prediction cares about. Drop rates are meaningful (e.g. women_800m dropped 98 of 254 candidate major-meet rows) — this is doing real work, not a no-op filter.

**Injury/withdrawal detection is fully wired end-to-end.** `src/injury_checker.py` scrapes news + meet-results recaps for injury/DNF signals, estimates recovery time, and either flags ("watch") or drops ("remove") an athlete from predictions. Both outcomes are visible on the dashboard: a "Watch" badge (linking to the real evidence) on flagged athletes, and a "Removed from predictions" panel (shown only when non-empty) for dropped ones.

*Working methods worth repeating next time this needs more visual work*:
- The Browser pane's screenshot capability was unreliable all session (three different failure modes hit across the day). Got burned by this twice: once from an agent-run critique's findings, once self-inflicted (lightened a glass-card tint for definition, didn't realize the tint itself was lightening the effective background enough to fail text contrast again).

Don't ask for craft-level feedback the agent can just act on directly ("this feels bland," "move the nav texture") — those got acted on directly, no question needed, and that was the right call each time.

**Verification methodology — read this before doing more contrast work, it will save an hour:**
- **Resolve CSS colours through a canvas, not a regex.** `getComputedStyle` returns `oklch(...)` strings in this app; naive parsing read them as RGB and reported **121/121 false failures**. Use `ctx.fillStyle = str; ctx.fillRect(...); getImageData(...)` — it handles any CSS colour including `oklch`/`oklab` and alpha.
- **The scanner can't see non-colour backgrounds.** Gradients need their stops extracted (take the lightest stop as worst case for light text); `background-image` photos and the `.track-surface` texture can't be measured at all and must be excluded, or they produce false failures. The Dashboard hero and the athlete photo hero were both pixel-verified in earlier sessions and are fine.
- **Steady-state figures for this app**: ~509–519 text elements across all six routes, **0 contrast failures**; plus 84 elements on the loading/error surfaces, 0 failures.
- **Force loading/error states by stubbing `window.fetch`** (`() => new Promise(() => {})` to hold loading, `() => Promise.reject(...)` for error), then restore it and confirm recovery. Don't assume those states look right.

**Figma Plugin API gotchas hit this session (all cost real debugging time):**
- **`resize()` pins BOTH axes.** This caused 21 clipped text nodes (text boxes fixed at 10px height) and two panels that silently clipped most of their rows. For text use `textAutoResize = "HEIGHT"`; for auto-layout frames set `primaryAxisSizingMode = "AUTO"`.
- **`figma.createAutoLayout()` defaults to an opaque white fill.** An uncleared fill on a page-content wrapper silently painted over the canvas gradients *and* the track-curve decoration. Clear `fills` on layout containers.
- **`arcData` with `innerRadius: 0` draws a filled pie, not a ring.** For a ring arc use a filled arc with a fractional `innerRadius` — or, if it needs to animate, build it as a stroked SVG path so `PATH_TRIM_END` can sweep it.
- **A frame's image export crops to its own declared bounds**, so decorative art positioned mostly outside the frame simply won't render.
- **Absolutely-positioned decoration must set `layoutPositioning = "ABSOLUTE"`**, or it joins the auto-layout stack and inflates the frame height.
- **The Figma MCP had a ~5-minute 503 outage** mid-session (every call, including `whoami`). Failed calls are **atomic** — nothing is applied — but verify state before re-running rather than assuming.

**Skills used:** `impeccable` (craft floor), `ui-ux-pro-max` (found bugs 3 and 4), `figma-use` / `figma-generate-design` / `figma-use-motion`. For `ui-ux-pro-max` on **existing** UI, use focused `--domain` searches — **not** `--design-system`, which is for new projects and would try to replace the established identity. Its first result set can be off-topic; retry once with a narrower query, as its own query contract instructs.

## Failed Attempts (tried, verified, did not help — don't redo without new evidence)

- **Event-specific models** (separate RandomForest per event group). Scored identically to one pooled model — `season_rank`/`season_percentile` already normalize per-discipline, so separate models add nothing.
- **`h2h_meetings` (count) as an additional feature** alongside `h2h_win_rate`: made results slightly worse. Not included.
- **Manual h2h blend at fixed weights**: tied with the trained-feature approach at best. Trained-feature chosen for architectural consistency (a manual post-hoc blend was the exact pattern that caused the recency-feature bug — didn't want to reintroduce it for h2h).
- **`src/scraper.py` (Wikipedia-based)**: fully non-functional, 0 rows ever. Deleted.
- **Including the DL Final's own results in `season_results_scraper.py`** (`rankingCategory in {"GW","DF"}`): produced a suspiciously large accuracy jump (63.8%) that turned out to be label leakage — the Final's own result was leaking into that year's training features. Fixed by restricting to `"GW"` only. **Lesson: a suspiciously good number is a signal to check harder, not a result to bank.**
- **Real per-athlete race-log scraping (all meets worldwide, not just the DL circuit)** (2026-08-23): confirmed via GraphQL introspection that WA's public API schema *has* fields for this (`getSingleCompetitorResultsDiscipline`/`getSingleCompetitor.resultsByDate`, taking a competitor id from `searchCompetitors`) — but the resolvers are dead server-side. Every combination of athlete id, year, and order-by argument tried (including with browser-matching headers) returned `resultsByDate: null`, while sibling fields on the same object (`activeYears`) resolved fine. `getSingleCompetitorSeasonBests` *does* work and confirms athletes' bests across all competitions (not just DL), but it's still one row per discipline per season — no more multi-meet granularity than what `season_results_scraper.py` already provides for the DL circuit specifically. ~~**Don't re-attempt this without new evidence the resolver was fixed** — it's a dead field, not a query-construction mistake.~~ **SUPERSEDED 2026-08-29 — see Next Steps 12.** Everything above is still true *of `resultsByDate`*, which is still dead. But a DIFFERENT field on the same object, **`resultsByYear`, resolves fine**, and returns an athlete's complete current season across every event they contest — including indoor races and odd distances no meeting-level scrape of the outdoor groups would find. The narrow lesson: a dead resolver on an object does not mean the object is empty. `src/athlete_profile_scraper.py` uses it. Note also that schema introspection is now BLOCKED (`__schema` returns 503 while ordinary queries succeed), so the field surface has to be mapped by requesting bogus fields and reading the validation errors back.
- **Widening `major_meets_scraper.py`'s Area Championships from European-only to all six continents** (African/Asian/South American/Oceania/NACAC added, 2026-08-23, sixth session): a live probe confirmed the calendar group (id 3660) is cleanly scoped (all six tagged `rankingCategory: "GL"`, no junior/indoor contamination) — the *code* concern that blocked this originally didn't hold up. But the *data* did: re-scraping (+150-390 rows/discipline) and retraining dropped accuracy 60.1% -> 58.6%, and re-tuning hyperparameters on the new data only recovered to 58.8% (best of 54 candidates), still below baseline. **This is a real regression, not tuning noise** — reverted via `git checkout -- src/major_meets_scraper.py` plus a re-scrape/re-train to restore the exact 60.1% baseline (confirmed byte-identical `outputs/*.pkl` after, since RF is deterministic with `random_state=42` on identical input). Likely cause: five of the six continental championships have much more field-quality variance than DL/Worlds/Olympics/Euro Champs, and the recognized-athlete filter doesn't fully compensate. **Don't redo without a per-continent accuracy breakdown first** (e.g. try adding just one continent at a time) if this gets revisited.
- **Three new "outcome, not just speed" feature candidates** (2026-08-23, sixth session, same day as the above): brainstormed features not derivable from the current 14 (all of which measure "how fast/far", not "did they actually win"), built and tested at fixed hyperparameters (isolated from tuning noise, same discipline as the Area Championships test above):
  - `final_top3_rate` — fraction of the season's *actual final-round* races (parsed from the raw toplist's `Pos` column, e.g. `"1"`/`"2f1"` = final, `"1h1"`/`"1sf1"` = heat/semi and excluded) where the athlete placed top 3. **58.8% alone** (-1.3pts). First hypothesis: `Pos` only existed in the original toplist-scrape rows (~55% of a discipline's rows), so ~45% defaulted to 0.0 for structural (source-confounded) reasons, not because the athlete never placed well. **Tested and falsified**: `season_results_scraper.py`/`major_meets_scraper.py` turned out to already fetch WA's `place` field per result and just never write it to the row (see the standalone fix, commit `c391a719`) — a one-line, zero-new-scraping-cost bug, not a missing capability. Backfilling it raised `Pos` coverage to ~99%, but accuracy came out **58.4%, still below baseline** (and no better than the original 58.8%). Real cause, confirmed by inspection: this data slice (DL circuit + major meets only, not an athlete's full season) gives most athletes just **1** final-round race in a given season — `final_top3_rate` is then a coin-flip point estimate from a single race, not a real behavioral tendency, and its raw correlation with the actual `dl_top3` label is 0.058 (essentially none). **The `Pos`-coverage fix was kept anyway** (correct, free, more complete data on disk) but the feature itself was not — don't re-attempt without a way to get more than ~1 final-round observation per athlete per season first (i.e. this is a data-density problem, not a coverage or engineering problem).
  - `dl_meets_share` — fraction of the season's marks that came from actual Diamond League venues (reusing the same `DL_VENUES` list `competition_weight` already checks). **59.3% alone** (-0.8pts). Root cause hypothesis: likely redundant with `weighted_season_best` (which already upweights DL-venue marks) rather than adding new information.
  - `dl_final_experience` — count of prior years (strictly before the label year, no leakage) this athlete made a DL Final in this discipline at all, from the full field in `dl_final_results.csv` (not just podiums). **58.2% alone** (-1.9pts). Root cause hypothesis: caps out low (dataset only spans 2018-2025) and likely correlates with `career_best`/`age` already, adding noise rather than signal.
  - **All three together: 57.1%** (-3.0pts) — worse than any single one, consistent with each contributing real noise rather than the drop being one bad feature diluted by two good ones. **Every one of the three regressed individually at the exact hyperparameters that produce the clean 60.1% baseline** — this isn't tuning noise, it's a real (if modest per-feature) negative signal. Code was reverted entirely (`git checkout -- src/train_model.py`, nothing had been committed) rather than left as an unused opt-in flag, matching how `h2h_meetings`/the manual h2h blend were handled above. (`final_top3_rate`'s `Pos`-coverage gap noted here was fixed and retested — see the next entry — and it still didn't help; the note above is superseded.)
- **Worldwide-style data expansion prototype** (2026-08-23, sixth session, same day): rather than commit to a full worldwide scrape untested, prototyped the cheapest reachable version first — World Athletics Continental Tour (id 3773) already has all-tier data (Gold/Silver/Bronze/Challenger) sitting behind the existing `major_meets_scraper.py` query, currently filtered to Gold only. Widening to all tiers, scoped to 3 disciplines (`men_100m`, `women_800m`, `men_LJ`) and 3 recent years (2023-2025, not the full 2018-2025 range) to keep it cheap: **~275+ meetings/year in this one competition group alone** (confirmed via a month-by-month count after the naive full-year query silently capped at exactly 100). Added +1187 to +1334 recognized-athlete rows per discipline even after the existing noise filter dropped ~2000+ unrecognized rows per discipline (this really is much noisier data, as originally suspected).
  - **This did fix the specific density problem `final_top3_rate` died on**: median final-round races per athlete-season went from 1.0 to 3.0-4.0 across all three disciplines. A from-scratch `final_top3_rate`-style correlation check on just this enriched slice improved in all three (men_100m 0.050→0.074, women_800m 0.054→0.105, men_LJ -0.031→0.038) — the first time in this session's whole accuracy investigation that "add more data" moved a signal in the right direction.
  - **But the real backtest, using the current shipped feature set (not a new feature), got worse**: 48.1% → 37.0% on just these 3 disciplines' 2023-2025 folds (13/27 → 10/27 correct). The lower-tier marks flow straight into `season_best`/`consistency`/`weighted_season_best`/`meets_count` for these athletes, and apparently dilute those aggregates with noisier, less-competitive-intensity marks faster than the added density helps. **Caveat: N=27 is small enough that this specific 3-hit swing carries real sampling noise of its own** — but it's consistent with, not contradicting, every other finding this session.
  - **Verdict: does not justify the full 32-discipline/7-year rollout.** The one encouraging signal (isolated correlation for a hypothetical feature) didn't survive contact with the real target metric once mixed into the existing aggregate features. Prototype data was stripped back out of `data/raw/{men_100m,women_800m,men_LJ}.csv` (filtered by its `ct_full_proto` source tag) to restore the shipped state — nothing was committed (data/raw/ is gitignored). **If this gets revisited, the fix would need to be about *how* lower-tier marks are weighted/blended into the aggregate features (e.g. a real competition-tier discount, not `competition_weight`'s current binary DL/major-vs-everything-else split), not just adding more of them at equal weight** — don't just re-run the same prototype expecting a different result.

## Known Limitations (real, understood, not bugs to re-chase)

- `season_results_scraper.py` (and `current_season_scraper.py`, same underlying mechanism, eighth session) only covers the Diamond League circuit, not an athlete's entire season everywhere they raced. An athlete who mostly raced non-DL meets still shows thinner history than reality. Real per-athlete profile scraping would close this fully but WA's API doesn't currently expose it (see Failed Attempts above) — the only way to close this now would be scraping every meeting worldwide via the general calendar, a much bigger undertaking with real rate-limit/politeness concerns at that scale.
- `men_5000m` has real labels for only 1 of 5 years (2024) — other years ran a 5km road race or didn't contest it in a form the scraper recognized. Auto-detected from real data, not hand-flagged, but the practical effect is thin signal for this one discipline.
- 2020 alone is excluded from training labels (COVID-era "Inspiration Games" exhibition, not a real qualifying Final). 2018/2019 are now included — see the Ground Truth note above for why they turned out not to need special handling after all.
- Two specific qualified athletes (Agnes Jebet Ngetich, women's 5000m; Yemisi Mabry, women's shot put) are genuinely absent from World Athletics toplists even at top-500 depth. Not fixable via more pagination.
- Women's Shot Put / Women's 5000m predictions are consistently short by 1-2 athletes.
- ~37% of athletes (86/235, seventh session's live audit) genuinely have no action photo on World Athletics' own system — `load_athlete_photo()` correctly returns `None` and the frontend falls back to an initials monogram. Not fixable from this endpoint; see the profile-page note above for the one real bug that *was* fixed here (a URL-format regex gap) and why it didn't move the number.
- The profile hero photo's crop position now comes from real per-photo face detection (`api.py`'s `detect_face_focus()`, OpenCV DNN, seventh session) with a `center 15%` fallback only when no confident face is found (~6 of the ~32 sampled athletes with a real photo, mostly side-profile or mid-air shots — verified live, see the profile-page note above for the full list). An unusual photo can still fall back to the imperfect default in that case; there's no further fix planned unless it turns out to matter often enough in practice.
- `outputs/predictions_latest.csv` and `data/standings.json` were both listed in `.gitignore` (correctly — they're regenerable, `run.py`/`live_fetcher.py`-owned outputs) but stayed **tracked** in git from an old commit (`ab909aa6`), predating whenever the gitignore rule was added. Noticed 2026-08-24, fixed the same day at the user's request via `git rm --cached` on both (commit `dac3adf1`) — files themselves untouched on disk, `git status` no longer shows them as dirty after a `run.py` run.
- Minor, not acted on: `lovable-error-reporting.ts` does nothing outside the Lovable editor; React Query is wired in but `usePredictions.ts` still does manual `fetch`/`useState`. (The `"qualified"` field used to be a hardcoded no-op — fixed eighth session, see above, it's real now.)
- **No cross-discipline "one athlete, one Final event" logic** (found via a user question, 2026-08-24 ninth session). Confirmed via real data, not a bug: predictions are built independently per discipline from each discipline's own real, live-scraped DL standings, with nothing anywhere checking whether the same athlete showing up as a contender in two different disciplines is actually possible at the real two-day Final (Sep 4-5, Brussels). Currently affects exactly 2 of ~237 athletes: Amy Hunt (Women's 100m + 200m — a completely normal, expected sprint double) and Jessica Hull (Women's 1500m + 5000m — a real but less certain distance double; her presence in *both* disciplines' real WA-scraped standings.json entries was independently verified, not a pipeline duplication bug). Tried to confirm via the real Brussels Final day-by-day schedule whether 1500m/5000m fall on different days (which would settle whether the double is even feasible this year) — not resolved, the detailed timetable wasn't publicly available/fetchable at the time of checking. Not fixed: there's no honest way to decide which single discipline an athlete will actually contest without fabricating that decision — WA doesn't publish final event-entry commitments this far ahead (same category of gap as the unmodeled DL wildcard provision, above). Rare enough (2 athletes) that it's flagged here rather than acted on.

0g. **"Weight top athletes' performances more when calculating accuracy" — asked 2026-08-25, and the honest answer was that it had NEVER been implemented, in any form.** Worth recording because it is easy to believe it had been: `competition_weight(venue)` exists, has "weight" in the name, and does weight *something* — but it weights **which meeting a mark came from** (1.3 major champs / 1.2 DL / 1.0 other) and feeds the `weighted_season_best` **feature**. It has nothing to do with athlete calibre and never touches the accuracy calculation. `class_weight` is RF class imbalance (tuned, and `None` beat `"balanced"` three separate times). There was no `sample_weight` anywhere in the repo.

   **What the headline metric actually is, stated plainly** (`_score_fold`, the only place accuracy is computed): per discipline, take the top 3 by predicted probability, intersect with the 3 who actually finished top 3, count hits, denominator exactly 3. Therefore: every hit is worth 1 (**the winner counts the same as 3rd**), **order is ignored entirely** (the right three in reverse order still scores 3/3), and **every discipline contributes exactly 3** regardless of field quality.

   Three separate things were then measured, and they are NOT interchangeable — two redefine the ruler, only one can actually make predictions better:

   **(a) Sample-weighting the TRAINING by athlete calibre — measured, does NOT work, not shipped.** This was the only one of the three that could genuinely improve the model, so it was judged on the *unchanged* metric across 10 seeds. All three schemes came out negative: `tiered` (top-3 rank counts triple, top-8 double) **-0.63 pts, 4/10 seeds**; `inv_sqrt` **-0.31, 4/10**; `season_percentile` **-0.22, 5/10**. Plausible reason: the model's whole job is separating top-3 from not-top-3, and down-weighting the "not" rows removes the contrast it learns from — and `season_rank`/`season_percentile` are *already features*, so weighting by them partly double-counts. **Don't re-attempt without a genuinely different weighting idea.**

   **(b) Position-weighting the METRIC (3/2/1) — implemented as a reported DIAGNOSTIC, deliberately NOT as the headline.** It reads **~68%** where the flat metric reads **59.7%**, and that gap is *mechanical*: weighting by finishing position inflates the number whenever hits concentrate on winners, which they do. It is a different ruler and **must never be quoted as an improvement or compared against the historical flat numbers** (60.1 / 58.0 / 59.7). `model_accuracy.txt` still holds exactly the flat number, and `test_flat_metric_is_still_order_blind` guards that definition.

   **(c) Field-depth weighting the METRIC — measured, essentially no effect, not shipped.** Weighting each discipline by how stacked it was (athletes within 2% of that event's best mark, normalised to mean 1) moved the number only **58.4% -> 59.6%**. That is a useful *null*: the model is not systematically better on thin events than on deep ones, so the flat per-discipline denominator isn't hiding a bias.

   **THE REAL FINDING, which is what the question was actually getting at.** Breaking the same predictions down by finishing position shows the flat number was averaging away something big:

   | actual finisher | found in our predicted top 3 |
   |---|---|
   | **winners** | **86.2%** (131/152) |
   | 2nd place | 55.0% (83/151) |
   | 3rd place | 39.0% (60/154) |

   plus the winner is the model's **own #1 pick 50.0%** of the time (76/152), against ~12.5% for picking at random from a field of eight. (Figures refreshed after the `weighted_season_best` fix and retrain; the shape is unchanged and the headline is still 59.7%.) **The model is far better at the thing that matters most than one averaged percentage suggests, and much weaker on the podium tail.** `train_and_backtest()` now prints this breakdown under every run (`_print_position_breakdown`), so it can't be forgotten again. The headline is untouched.

0i. **Latent bug that took the whole test suite down, worth knowing before adding any test that imports `src/` (`0566e74e`).** Nine modules in `src/` each did `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)` **at import time**. Each wraps the *same* underlying buffer, so with two of them imported into one process the first wrapper garbage-collected closes that buffer under the second, and every later write dies with `ValueError: I/O operation on closed file`. Adding `tests/test_injury_checker.py` was enough to trigger it — the failure was **latent and GC-timing dependent**, so the suite could have started failing on its own at any point. Every swap is now a **no-op when stdout is already UTF-8**, so the first wins and the rest do nothing; scripts keep the behaviour they need on a cp1252 Windows console. **`pytest.ini` still needs `-s`** for the same family of reasons — don't "fix" that away. Related trap from the same day: three of those files (`h2h_calculator`, `h2h_scraper`, `live_fetcher`) carry a **UTF-8 BOM**, so any tooling that reads them must use `utf-8-sig` or it will report a bogus `invalid non-printable character U+FEFF`.

0i2. **`weighted_season_best` was inverted for track events, and fixing it requires a RETRAIN — don't repeat the mistake I made here.** It computed `mark * competition_weight` then took `min()` for track. Multiplying a **time** by 1.2 makes it look *slower*, so `min()` systematically picked whichever mark came from the **weakest** meet — the exact opposite of the intent, and of what the landing page advertises. Bromell's `weighted_season_best` read **11.892** for a 9.91 sprinter. Track now divides, field still multiplies; fixed identically in `train_model.add_new_features` and `feature_builder.py`. Backtest 58.45% → 58.82% over 10 seeds (sd 0.76 → 0.62), but the justification is correctness, not the delta.

   **The trap:** fixing a feature in both places without retraining leaves `run.py` feeding the *corrected* feature into a model trained on the *broken* one — a silent train/serve mismatch that nothing errors on. Caught before pushing. Always follow a feature fix with `python src/train_model.py --with-recency --with-h2h --with-schedule` and then `python run.py --no-scrape`.

0o. **RESOLVED 2026-08-25 - the head-to-head data was substantially wrong, and fixing it cost accuracy. Shipped anyway; read why before "improving" it back.** `h2h_rates.csv` claimed **Yared Nuguse beat Jakob Ingebrigtsen 12-0 in the 1500m**, which is false and was rendered on a user-facing panel.

   **Three compounding causes, all confirmed against `meet_results.csv`:**
   - `h2h_scraper.py`'s `parse_results_table` strips `Pos` to digits and **never records which ROUND a row came from**, so heats, semis and finals land under one `meet` name. **2005 of 10601** athlete/meet/discipline groups have more than one row.
   - `calculate_h2h` did `places = dict(zip(meet_df["athlete"], meet_df["place"]))`, which **silently kept each athlete's LAST row**. At the 2023 World Championships Jakob's rows are `[1, 13]` and Nuguse's are `[4, 1, 5]`, so the comparison actually made was **13 against 5** - handing Nuguse a championship Jakob won.
   - The pairwise loop walked the **ROW list, not unique athletes**, so one meeting between a 2-row and a 3-row athlete counted as up to **6** "meetings" - the same wrong comparison repeated, which is what produced clean sweeps.

   **Fix (`one_row_per_athlete` + iterate the de-duplicated frame):** collapse to each athlete's **best (lowest) place** per meet, skip pairs on **equal** places (equal placings can only mean different heats - counting them either way invents a result), and iterate unique athletes. No re-scrape needed; `meet_results.csv` already held the rows.

   **Result: perfect sweeps among pairs with >=5 meetings fell 64% -> 14%**, and mean meetings per pair 2.85 -> 1.26 (the ~2.3x inflation the duplicate loop was adding).

   | arm | mean | vs. buggy |
   |---|---|---|
   | buggy data + `h2h_win_rate` (what shipped) | 72.27% | - |
   | fixed data + `h2h_win_rate` | 71.70% | **-0.57**, 2/10 seeds |
   | fixed data, `h2h_win_rate` dropped entirely | 71.87% | -0.39, 4/10 seeds |

   The fabricated sweeps were acting as a **strength proxy** (a better athlete accrued more phantom wins), so the feature was partly re-encoding `season_percentile` - the same "redundancy is load-bearing" effect as the duplicate mark columns in 0p. Correcting it also thins the data: Final-field rows with a real (non-default) h2h value fall **70.6% -> 63.1%**, because best-place collapsing discards ties.

0p. **The feature-importance table was audited 2026-08-25 at the user's request. Three real findings, and three clean negatives that killed my own hypothesis. Read this before proposing anything "ability-based" again.**

   **FINDING 1 - the headline metric measures a task the site never performs.** `_score_fold` picks its top 3 from **every athlete in that discipline-year's toplist (~101)**. `run.py` only ever ranks the **~8-10 athletes in WA's standings**. Scored on the real task - pick 3 from the athletes who actually contested that Final - the current model scores **72.3%**, not 59.7%. Per finishing position it is **95% / 70% / 54%**, not the 87%/-/37% on record. **The "model can't find third places" diagnosis in 0h is substantially a scoring-pool artifact.** Recommend reporting both numbers and labelling which is which; 59.7% is not wrong, it just answers "find the podium among 101 names", which is nobody's question.

   **FINDING 2 - four of the fifteen features are the same number, measured.** `season_best` vs `career_best` **+1.000** (they are *equal* in **67%** of rows - the history is too thin to differ, which is also why `pb_gap` is last at .017), vs `wind_adj_season_best` **+1.000**, vs `weighted_season_best` **+0.997**; `season_rank` vs `season_percentile` **-0.997**. Gini importance splits credit arbitrarily among collinear columns, so the table partly measures *how many copies of a thing exist*.

   **FINDING 3 - raw marks carry no pooled signal.** Correlation with the target: `season_best` **-0.002**, `career_best` -0.002, `weighted_season_best` -0.003, `wind_adj_season_best` -0.002, `recent_trend` +0.002. One pooled model across 32 disciplines puts 9.79s, 74.04m and 3:27.62 in one column with no discipline indicator. Only the per-discipline-normalised `season_rank`/`season_percentile` survive (+/-0.275 pooled, **+0.546** within a real field).

   **NEGATIVE 1 - training on the DEPLOYMENT population gains nothing.** The hypothesis was strong: 68% of training rows have `meets_count <= 1` and a **0.01%** podium rate, 12% have `meets_count >= 4` and **23.25%**, so most of what the forest learns is "circuit regular vs. random toplist name" - a distinction with no variance left in the field `run.py` applies it to (real field median `meets_count` = 4). Controlled test, same features, same test rows, same folds, fitting rows the only difference: **+0.26 pts, 7/10 seeds** - inside the noise floor. Real benefit is stability only (sd 0.33 vs 0.71). **The artifact is real and it is not what is capping accuracy.**

   **NEGATIVE 2 - magnitude-based ability features add nothing, and failed a shuffled control.** Built `sb_z` (season best as a z-score within its discipline-year, sign-flipped so higher is always better) and `gap_to_leader` (distance from the field's best mark in field SDs) - unit-free, so they work across all 32 disciplines where raw marks cannot, and they carry what a RANK throws away (2nd by 0.02s vs 2nd by 0.6s). In isolation `sb_z` correlates **+0.515** with the target, nearly as strong as `season_percentile`. Added to the model: `sb_z` **-0.20 (4/10)**, `gap_to_leader` **-0.37 (4/10)**, both **-0.70 (2/10)**. Decisively, **a SHUFFLED `sb_z` scored the identical -0.20** - so the real column contributes nothing over `season_percentile`. Don't rebuild these.

   **NEGATIVE 3 - and this one is informative: removing the four measured duplicates HURTS, -1.05 pts (1/10 seeds).** A lean set plus both new features was worst of all (-1.24). Provably collinear columns are not waste here: with `max_features` sampling, extra correlated copies raise the chance the mark signal is in any given split's candidate set, which acts as implicit upweighting. **So the ability signal matters MORE than the importance table suggests, and the "redundancy" is load-bearing. Do not tidy it away.**

Population framing, magnitude features and de-duplication were each tested honestly and each did nothing or hurt. The two real opportunities left are **not** accuracy features: fix the head-to-head data (0o - known-wrong data feeding the 5th-largest feature), and report the metric that matches the product (Finding 1).     **What genuinely does NOT transfer, and is the real work:**
    - **Field selection.** DL = points standings, top N, which `run.py` mirrors exactly. Worlds/Olympics = entry standard + world ranking + a hard **max 3 per country**. Nothing in the current selection logic models a national quota. Predicting a medal from a known start list is the existing problem; predicting who is even in the field is not.
    - **Rounds.** A DL Final is one race; championships run heats → semis → final, so "will they reach the final" is a question the model has no concept of.
    - **Event coverage.** Worlds/Olympics add relays, marathon, race walks and combined events; the current 32 are individual track and field.
    - **Frequency.** Worlds biennial, Olympics quadrennial — the back-history is fine but new labels accrue far more slowly than a DL season provides.

    **FIRST STEP when this does start, and it needs no new scraping:** train on DL Finals, test on championship finals. That validates or kills the transfer assumption for the cost of one backtest, before any work on selection logic or rounds.

11. **"Is the Final split between Zürich and Brussels?" — asked 2026-08-29 by the user, who had watched Zürich. Answered against World Athletics' own data, and the check found a real error nobody had noticed.**

    **The answer: not this year.** WA's calendar (`getMinisiteCalendarEvents`, competitionGroup 627) tags Weltklasse Zürich (26–27 Aug) `rankingCategory: "GW"` — a regular scoring meeting — and every one of its event groups is GW too, with no "DF" group anywhere in it. Exactly one 2026 meeting is DF: **Allianz Memorial van Damme, Brussels, 4 Sep**, and it has `hasApiResults: false` because it has not happened. So no discipline's Final has been contested; all 32 are still to come.

    **But the instinct was well-founded, and the format is real.** `find_final_competition_ids` per season: **2018 and 2019 were genuinely split Finals** — Zürich *and* Brussels, two meetings both tagged DF (2019: Zürich 28 Aug + Brussels 5 Sep). 2021, 2022 and **2025** had the Final AT Zürich, which is almost certainly where the impression came from: the same stadium, in 2025 on the same late-August weekend, was the Final. In 2026 the Final moved to Brussels and Zürich reverted to a scoring meeting. `dl_final_results_scraper.py` already aggregates multiple DF meetings correctly (which is why 2018/2019 carry 320/327 label rows against 223–251 for single-venue years) — that half was never broken.

    **What WAS broken: `api.py`'s `MEETS` list had drifted from the real calendar, and the Schedule page was rendering it to readers as fact.** Five wrong rows: it opened the season with **"08 May Doha", a meeting that does not exist** (the opener was 16 May in **Shaoxing/Keqiao**, which the list called "Shanghai"); **Doha's real date, 19 Jun, was missing entirely**; Paris was 26 Jun not 28 Jun; Eugene 04 Jul not 03–04 Jul. Nothing caught it because MEETS only feeds display and `meetings_remaining()`, and by late season every past date answers that arithmetic identically — **the errors became invisible exactly when they stopped changing a number.** Now corrected and verified 0 disagreements against WA.

    **Three structural fixes, not just corrected values:**
    - **`src/dl_calendar.py`** fetches WA's calendar for any season and diffs it against `MEETS` (`python src/dl_calendar.py`). It also reports how many meetings are DF and warns explicitly when a season has more than one.
    - **`tests/test_dl_calendar.py`** (8 tests) pins `MEETS` to committed snapshots — `tests/fixtures/wa_dl_calendar_2026.json` and **`wa_dl_calendar_2019.json`, kept specifically because 2019 is the real split-Final counterexample**. Offline, no network.
    - **The Final is now an explicit `"final": True` flag, not "the last entry in the list".** Under the old rule a split Final's *first leg* would be scored as a qualifying meeting, so `meetings_remaining()` would have claimed DL points were still winnable **at a Final**. There is a test for exactly that, built from the real 2019 calendar. `compute_meet_statuses` falls back to last-index when nothing is flagged, so the older bare-list tests still mean what they meant.
    - Two-day meetings now carry `dateEnd` (Lausanne, Silesia, Zürich, Eugene) and are judged "done" on their **last** day, not their first — the old list picked day 2 for three of them and day 1 for the fourth, with no rule. The Schedule page renders "26–27 Aug".

    **Carry this into Phase 2 (item 10):** a competition's structure must come from **WA's own `rankingCategory`**, never from position in a list or a hand-typed schedule. Championships have rounds, multi-day finals and split legs; the assumption that "the last thing in the calendar is the final" is already false for two seasons of the Diamond League's own history.

13. **`src/athlete_career.py` — what World Athletics SAYS, kept apart from what this project computes.** Honours, world ranking and personal bests, read from `data/athlete_profiles/`. 18. **THE EIGHTEENTH SESSION (2026-09-01) — closed 0o's open half, and the scraper turned out to have been wrong in four more ways.** `h2h_scraper.py` now records which race a row came from; `h2h_calculator.py` compares athletes one race at a time instead of collapsing a whole meeting. **This is the first h2h change in this project that IMPROVED accuracy** — 0o's correction cost −0.57, this one is **+1.22 pts** on the real-field metric, better on 9 of 10 paired seeds and worse on 0.

    **What 0o asked for.** A meeting is not a contest. Two athletes are now only compared when they were on the same start list, which needs the race label (`race`, from the table's full section path) and the heat within it (`heat`, from the table's own Heat/Group column). A pair meeting in both a heat and the final counts twice; they raced twice.

    **Four more defects, all found by reading the pages rather than the code, all live for the whole life of the file:**
    - **The podium was missing from every race in the dataset.** Wikipedia renders positions 1-3 as a medal template with **no text in the cell**, so `int(cell.text)` returned nothing. **2825 of 13040 rows (21.7%) had no place at all, and they were the podiums.** Now read from the template's `data-sort-value` (or the medal image's alt text); no-place rows are down to 1.3%.
    - **The 400m hurdles did not exist.** `classify_table` matched on ANY keyword, and the sprint hurdles' were `["110", "hurdle"]` — the word "hurdle" alone was enough, and they are tested first. **`men_400h` and `women_400h` held zero rows**; Warholm, Benjamin, dos Santos, Bol and McLaughlin-Levrone were all filed as sprint hurdlers. 30 disciplines → **32**.

Hurdles-or-not is now decided first, from either spelling (`looks_like_hurdles`), and the distance alone picks the event.
    - **The whole 2025 Diamond League season was missing.** Older/newer meeting pages head each table with just the event (`400 metres hurdles`) under a `Men`/`Women` section, so the caption had no gender to match on and nothing classified. 21. **THE NINETEENTH SESSION (2026-09-01) — the "missing World Championships" were never missing, and looking found the opposite defect.** Next Steps 5 claimed only 2019's Worlds were in the pipeline. The data says otherwise, and always did: **2019 Doha 355 rows, 2022 Oregon 355, 2023 Budapest 359, 2025 Tokyo 363**, all in `data/raw/*.csv` under `source == "major_meet"`. Nothing was missing. `hasApiResults` is true for every candidate meeting in every year, so nothing was being silently dropped either.

    **What was actually wrong: the scraper collected meetings it had no business collecting, and the docstring said so.** `SERIES_NAME_EXCLUDE` was a keyword list ("U20", "Indoor", "Cross Country", "Race Walking", "Road Running", "Relays", "Combined Events") applied to the World Athletics Series group. 2018 has no senior outdoor World Championships at all — they are 2019, 2022, 2023, 2025 in this window — and the list admitted **two** meetings that year, because neither name contains any of its words:
    - **"IAAF Continental Cup"**, a continental TEAM competition, which is not a World Championships under any reading. **220 rows in the training data.**
    - **"IAAF World Half Marathon Championships"**, a road championship whose excluding keyword would have had to be "Half Marathon". Harmless in practice (no event maps to any of the 32 disciplines) and wrong in principle.

    **The fix reads WA's own field.** The senior outdoor Worlds carry `rankingCategory == "OW"`, which is already in the calendar query. Verified across every year in `YEARS`: OW appears in exactly 2019/2022/2023/2025 and in none of 2018/2021/2024 — the years with no Worlds. Everything the keyword list meant to exclude is GW, C or F. This is the same move `CONTINENTAL_TOUR` already makes with `"A"`.

    **Measured, and the honest answer is "no accuracy claim".** Removing the 220 rows scored **+0.48 pts on 7/10 paired seeds** — which looks like a win until the control runs. Removing the SAME NUMBER of 2018 major-meet rows at random scored **+0.33 on 6/10**. The gap is noise. This is a correctness fix and is described as one; see [[feedback-measure-features-across-seeds]] for why the control is not optional.
