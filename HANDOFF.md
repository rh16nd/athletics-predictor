## Goal

## Current State

**Model**: RandomForestClassifier, `n_estimators=200, max_depth=16, min_samples_leaf=1, class_weight=None` (`DEFAULT_MODEL_PARAMS` in `train_model.py` — walk-forward tuned via `--tune`, re-tune whenever the feature set, training-set size, OR data-quality filtering changes, since the winning config shifts each time — it's flipped `class_weight` None↔"balanced" twice across five re-tunes so far; hyperparameter search on a dataset this size (~459 rows) is itself somewhat noisy, so don't read too much into which single config "won" a given round). 14 features, **all carrying real signal**:
`season_best, career_best, pb_gap, meets_count, consistency, yoy_improvement, age, season_rank, season_percentile, weighted_season_best, wind_adj_season_best, recent_trend, days_since_last, h2h_win_rate`

**Backtest accuracy: two numbers, and which one you quote matters (2026-08-25).** **71.9%** (330/459) is the top-3 hit rate among the athletes who actually contested the Final — **the task `run.py` performs**, and what the site now displays. **57.7%** (265/459) is the historical figure, which picks 3 from a discipline-year's whole ~101-athlete toplist; every other number in this document is that ruler, so it stays the comparison baseline. Both come off the same predictions and are written to `outputs/model_metrics.json`. The toplist figure moved 59.7% → 57.7% when the head-to-head data was corrected (Next Steps 0o — the fix costs accuracy and was shipped anyway). — **read the caveat before quoting this.** It moved twice on 2026-08-25: 60.1% -> 58.0% from the Mile/1500m data fix (Next Steps 0c), then 58.0% -> 59.7% from adding `gap_variability` (0f). Both numbers are the seed-42 walk-forward result, the convention this project has always reported. **The seed-averaged gain from `gap_variability` is only +0.68 pts, not +1.7** — a single seed swings +/-1 point on this dataset, so 59.7 vs 58.0 overstates the real improvement. Honest expectation is ~58.5%. — walk-forward validated: trained on every year strictly before each test year, scored independently on 2021, 2022, 2023, 2024, and 2025 (5 folds, not one fixed holdout). The deployed model is refit on all 7 label years after validation. Trained on all 32 live-predicted disciplines (`men_5000m` has thin signal — see Known Limitations). This is essentially flat vs. the same-day earlier number (60.3%) despite two real additions since (major meets beyond the DL circuit, and a noise filter) — see the Failed Attempts / project memory for why that's an expected outcome of this dataset's size, not a wasted afternoon.

**Ground truth is real, not hand-typed.** `src/dl_final_results_scraper.py` pulls actual Diamond League Final results (2018-2025, excluding 2020) directly from World Athletics' own public GraphQL API — the same API the site's own frontend uses (`x-api-key` is a public key shipped in every page load, not a secret). It finds each year's Final by filtering `rankingCategory == "DF"` and reads which disciplines were contested (and under what name — e.g. "Mile" some years instead of "1500 Metres") directly from what's present in the response, rather than a hand-maintained list. **2018/2019 were initially assumed to need a different scoring format** (the Final was split across two meetings, Zurich + Brussels) and skipped — checking the actual per-meeting data (2026-08-23) showed each of the 32 disciplines' DF group appears at exactly one of the two meetings, never both, so it's a two-city Final, not a split score. The scraper now aggregates across however many DF meetings a year has instead of assuming exactly one. 2020 (COVID-era "Inspiration Games" exhibition) is still deliberately excluded.

**Training features go beyond a season-best toplist.** `src/season_results_scraper.py` pulls every *regular-season* Diamond League meeting's results (not just the Final — that would leak the label) for 2018-2025 (excluding 2020), giving real multiple-marks-per-athlete-per-season data. This is what makes `meets_count`/`consistency`/`recent_trend` real features instead of structural zeros.

**Beyond the DL circuit: `src/major_meets_scraper.py`** (added 2026-08-23, user-requested "meets with the big athletes") adds real per-meeting results from the Olympic Games, the senior outdoor World Athletics Championships, World Athletics Continental Tour **Gold tier only** (`rankingCategory == "A"`, filtered out of a much larger Silver/Bronze/Challenger pool), and the European Athletics Championships (the other five Area Championships — African/Asian/American/Oceania/NACAC — were deliberately left out per the user, quality varies too much by continent). These groups were found via `getCalendarEvents`'s own `options.competitionGroups`/`rankingCategories` introspection, not guessed.

**Both per-meeting scrapers filter to "recognized" athletes only** (`dl_final_results_scraper.load_recognized_names`): a row is kept only if that athlete appears somewhere in the discipline's own toplist (any year, not just that exact year — deliberately lenient about single-year toplist gaps). This exists because a big meeting can still have a weak field in a discipline that isn't its main draw (e.g. a field-filler making a Continental Tour Gold meeting's javelin final) — keeping those marks would add noise (thin, one-off meets_count/consistency signal) rather than real information about the athletes DL Final prediction cares about. Drop rates are meaningful (e.g. women_800m dropped 98 of 254 candidate major-meet rows) — this is doing real work, not a no-op filter.

**Injury/withdrawal detection is fully wired end-to-end.** `src/injury_checker.py` scrapes news + meet-results recaps for injury/DNF signals, estimates recovery time, and either flags ("watch") or drops ("remove") an athlete from predictions. Both outcomes are visible on the dashboard: a "Watch" badge (linking to the real evidence) on flagged athletes, and a "Removed from predictions" panel (shown only when non-empty) for dropped ones.

**Verification methodology — read this before doing more contrast work, it will save an hour:**
- **Resolve CSS colours through a canvas, not a regex.** `getComputedStyle` returns `oklch(...)` strings in this app; naive parsing read them as RGB and reported **121/121 false failures**. Use `ctx.fillStyle = str; ctx.fillRect(...); getImageData(...)` — it handles any CSS colour including `oklch`/`oklab` and alpha.
- **The scanner can't see non-colour backgrounds.** Gradients need their stops extracted (take the lightest stop as worst case for light text); `background-image` photos and the `.track-surface` texture can't be measured at all and must be excluded, or they produce false failures. The Dashboard hero and the athlete photo hero were both pixel-verified in earlier sessions and are fine.
- **Steady-state figures for this app**: ~509–519 text elements across all six routes, **0 contrast failures**; plus 84 elements on the loading/error surfaces, 0 failures.
- **Force loading/error states by stubbing `window.fetch`** (`() => new Promise(() => {})` to hold loading, `() => Promise.reject(...)` for error), then restore it and confirm recovery. Don't assume those states look right.

**Figma Plugin API gotchas hit this session (all cost real debugging time):**
- **`resize()` pins BOTH axes.** This caused 21 clipped text nodes (text boxes fixed at 10px height) and two panels that silently clipped most of their rows. For text use `textAutoResize = "HEIGHT"`; for auto-layout frames set `primaryAxisSizingMode = "AUTO"`.
- **`figma.createAutoLayout()` defaults to an opaque white fill.** An uncleared fill on a page-content wrapper silently painted over the canvas gradients *and* the track-curve decoration. Clear `fills` on layout containers.
- **`arcData` with `innerRadius: 0` draws a filled pie, not a ring.** For a ring arc use a filled arc with a fractional `innerRadius` — or, if it needs to animate, build it as a stroked SVG path so `PATH_TRIM_END` can sweep it.
- **A frame's image export crops to its own declared bounds**, so decorative art positioned mostly outside the frame simply won't render.
- **Absolutely-positioned decoration must set `layoutPositioning = "ABSOLUTE"`**, or it joins the auto-layout stack and inflates the frame height.
- **The Figma MCP had a ~5-minute 503 outage** mid-session (every call, including `whoami`). Failed calls are **atomic** — nothing is applied — but verify state before re-running rather than assuming.

- **Three new "outcome, not just speed" feature candidates** (2026-08-23, sixth session, same day as the above): brainstormed features not derivable from the current 14 (all of which measure "how fast/far", not "did they actually win"), built and tested at fixed hyperparameters (isolated from tuning noise, same discipline as the Area Championships test above):
  - `final_top3_rate` — fraction of the season's *actual final-round* races (parsed from the raw toplist's `Pos` column, e.g. `"1"`/`"2f1"` = final, `"1h1"`/`"1sf1"` = heat/semi and excluded) where the athlete placed top 3. **58.8% alone** (-1.3pts). Backfilling it raised `Pos` coverage to ~99%, but accuracy came out **58.4%, still below baseline** (and no better than the original 58.8%). Real cause, confirmed by inspection: this data slice (DL circuit + major meets only, not an athlete's full season) gives most athletes just **1** final-round race in a given season — `final_top3_rate` is then a coin-flip point estimate from a single race, not a real behavioral tendency, and its raw correlation with the actual `dl_top3` label is 0.058 (essentially none). **The `Pos`-coverage fix was kept anyway** (correct, free, more complete data on disk) but the feature itself was not — don't re-attempt without a way to get more than ~1 final-round observation per athlete per season first (i.e. this is a data-density problem, not a coverage or engineering problem).

Root cause hypothesis: caps out low (dataset only spans 2018-2025) and likely correlates with `career_best`/`age` already, adding noise rather than signal.

Code was reverted entirely (`git checkout -- src/train_model.py`, nothing had been committed) rather than left as an unused opt-in flag, matching how `h2h_meetings`/the manual h2h blend were handled above. (`final_top3_rate`'s `Pos`-coverage gap noted here was fixed and retested — see the next entry — and it still didn't help; the note above is superseded.)

0g. **"Weight top athletes' performances more when calculating accuracy" — asked 2026-08-25, and the honest answer was that it had NEVER been implemented, in any form.** Worth recording because it is easy to believe it had been: `competition_weight(venue)` exists, has "weight" in the name, and does weight *something* — but it weights **which meeting a mark came from** (1.3 major champs / 1.2 DL / 1.0 other) and feeds the `weighted_season_best` **feature**. It has nothing to do with athlete calibre and never touches the accuracy calculation. `class_weight` is RF class imbalance (tuned, and `None` beat `"balanced"` three separate times). There was no `sample_weight` anywhere in the repo.

   **What the headline metric actually is, stated plainly** (`_score_fold`, the only place accuracy is computed): per discipline, take the top 3 by predicted probability, intersect with the 3 who actually finished top 3, count hits, denominator exactly 3. Therefore: every hit is worth 1 (**the winner counts the same as 3rd**), **order is ignored entirely** (the right three in reverse order still scores 3/3), and **every discipline contributes exactly 3** regardless of field quality.

   Three separate things were then measured, and they are NOT interchangeable — two redefine the ruler, only one can actually make predictions better:

   **(a) Sample-weighting the TRAINING by athlete calibre — measured, does NOT work, not shipped.** This was the only one of the three that could genuinely improve the model, so it was judged on the *unchanged* metric across 10 seeds. All three schemes came out negative: `tiered` (top-3 rank counts triple, top-8 double) **-0.63 pts, 4/10 seeds**; `inv_sqrt` **-0.31, 4/10**; `season_percentile` **-0.22, 5/10**. Plausible reason: the model's whole job is separating top-3 from not-top-3, and down-weighting the "not" rows removes the contrast it learns from — and `season_rank`/`season_percentile` are *already features*, so weighting by them partly double-counts. **Don't re-attempt without a genuinely different weighting idea.**

   **(b) Position-weighting the METRIC (3/2/1) — implemented as a reported DIAGNOSTIC, deliberately NOT as the headline.** It reads **~68%** where the flat metric reads **59.7%**, and that gap is *mechanical*: weighting by finishing position inflates the number whenever hits concentrate on winners, which they do. It is a different ruler and **must never be quoted as an improvement or compared against the historical flat numbers** (60.1 / 58.0 / 59.7). `model_accuracy.txt` still holds exactly the flat number, and `test_flat_metric_is_still_order_blind` guards that definition.

0i. **Latent bug that took the whole test suite down, worth knowing before adding any test that imports `src/` (`0566e74e`).** Nine modules in `src/` each did `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)` **at import time**. Each wraps the *same* underlying buffer, so with two of them imported into one process the first wrapper garbage-collected closes that buffer under the second, and every later write dies with `ValueError: I/O operation on closed file`. Adding `tests/test_injury_checker.py` was enough to trigger it — the failure was **latent and GC-timing dependent**, so the suite could have started failing on its own at any point. Every swap is now a **no-op when stdout is already UTF-8**, so the first wins and the rest do nothing; scripts keep the behaviour they need on a cp1252 Windows console. **`pytest.ini` still needs `-s`** for the same family of reasons — don't "fix" that away. Related trap from the same day: three of those files (`h2h_calculator`, `h2h_scraper`, `live_fetcher`) carry a **UTF-8 BOM**, so any tooling that reads them must use `utf-8-sig` or it will report a bogus `invalid non-printable character U+FEFF`.

0i2. **`weighted_season_best` was inverted for track events, and fixing it requires a RETRAIN — don't repeat the mistake I made here.** It computed `mark * competition_weight` then took `min()` for track. Multiplying a **time** by 1.2 makes it look *slower*, so `min()` systematically picked whichever mark came from the **weakest** meet — the exact opposite of the intent, and of what the landing page advertises. Bromell's `weighted_season_best` read **11.892** for a 9.91 sprinter. Track now divides, field still multiplies; fixed identically in `train_model.add_new_features` and `feature_builder.py`. Backtest 58.45% → 58.82% over 10 seeds (sd 0.76 → 0.62), but the justification is correctness, not the delta.

   **The trap:** fixing a feature in both places without retraining leaves `run.py` feeding the *corrected* feature into a model trained on the *broken* one — a silent train/serve mismatch that nothing errors on. Caught before pushing. Always follow a feature fix with `python src/train_model.py --with-recency --with-h2h --with-schedule` and then `python run.py --no-scrape`.

0o. **RESOLVED 2026-08-25 - the head-to-head data was substantially wrong, and fixing it cost accuracy. Shipped anyway; read why before "improving" it back.** `h2h_rates.csv` claimed **Yared Nuguse beat Jakob Ingebrigtsen 12-0 in the 1500m**, which is false and was rendered on a user-facing panel.

   **Three compounding causes, all confirmed against `meet_results.csv`:**
   - `h2h_scraper.py`'s `parse_results_table` strips `Pos` to digits and **never records which ROUND a row came from**, so heats, semis and finals land under one `meet` name. **2005 of 10601** athlete/meet/discipline groups have more than one row.
   - `calculate_h2h` did `places = dict(zip(meet_df["athlete"], meet_df["place"]))`, which **silently kept each athlete's LAST row**. At the 2023 World Championships Jakob's rows are `[1, 13]` and Nuguse's are `[4, 1, 5]`, so the comparison actually made was **13 against 5** - handing Nuguse a championship Jakob won.
   - The pairwise loop walked the **ROW list, not unique athletes**, so one meeting between a 2-row and a 3-row athlete counted as up to **6** "meetings" - the same wrong comparison repeated, which is what produced clean sweeps.

   **Fix (`one_row_per_athlete` + iterate the de-duplicated frame):** collapse to each athlete's **best (lowest) place** per meet, skip pairs on **equal** places (equal placings can only mean different heats - counting them either way invents a result), and iterate unique athletes. No re-scrape needed; `meet_results.csv` already held the rows.

   | arm | mean | vs. buggy |
   |---|---|---|
   | buggy data + `h2h_win_rate` (what shipped) | 72.27% | - |
   | fixed data + `h2h_win_rate` | 71.70% | **-0.57**, 2/10 seeds |
   | fixed data, `h2h_win_rate` dropped entirely | 71.87% | -0.39, 4/10 seeds |

0p. **The feature-importance table was audited 2026-08-25 at the user's request. Three real findings, and three clean negatives that killed my own hypothesis. Read this before proposing anything "ability-based" again.**

   **FINDING 1 - the headline metric measures a task the site never performs.** `_score_fold` picks its top 3 from **every athlete in that discipline-year's toplist (~101)**. `run.py` only ever ranks the **~8-10 athletes in WA's standings**. Scored on the real task - pick 3 from the athletes who actually contested that Final - the current model scores **72.3%**, not 59.7%. Per finishing position it is **95% / 70% / 54%**, not the 87%/-/37% on record. **The "model can't find third places" diagnosis in 0h is substantially a scoring-pool artifact.** Recommend reporting both numbers and labelling which is which; 59.7% is not wrong, it just answers "find the podium among 101 names", which is nobody's question.

   **FINDING 2 - four of the fifteen features are the same number, measured.** `season_best` vs `career_best` **+1.000** (they are *equal* in **67%** of rows - the history is too thin to differ, which is also why `pb_gap` is last at .017), vs `wind_adj_season_best` **+1.000**, vs `weighted_season_best` **+0.997**; `season_rank` vs `season_percentile` **-0.997**. Gini importance splits credit arbitrarily among collinear columns, so the table partly measures *how many copies of a thing exist*.

   **FINDING 3 - raw marks carry no pooled signal.** Correlation with the target: `season_best` **-0.002**, `career_best` -0.002, `weighted_season_best` -0.003, `wind_adj_season_best` -0.002, `recent_trend` +0.002. One pooled model across 32 disciplines puts 9.79s, 74.04m and 3:27.62 in one column with no discipline indicator. Only the per-discipline-normalised `season_rank`/`season_percentile` survive (+/-0.275 pooled, **+0.546** within a real field).

   **NEGATIVE 1 - training on the DEPLOYMENT population gains nothing.** The hypothesis was strong: 68% of training rows have `meets_count <= 1` and a **0.01%** podium rate, 12% have `meets_count >= 4` and **23.25%**, so most of what the forest learns is "circuit regular vs. random toplist name" - a distinction with no variance left in the field `run.py` applies it to (real field median `meets_count` = 4). Controlled test, same features, same test rows, same folds, fitting rows the only difference: **+0.26 pts, 7/10 seeds** - inside the noise floor. Real benefit is stability only (sd 0.33 vs 0.71). **The artifact is real and it is not what is capping accuracy.**

   **NEGATIVE 2 - magnitude-based ability features add nothing, and failed a shuffled control.** Built `sb_z` (season best as a z-score within its discipline-year, sign-flipped so higher is always better) and `gap_to_leader` (distance from the field's best mark in field SDs) - unit-free, so they work across all 32 disciplines where raw marks cannot, and they carry what a RANK throws away (2nd by 0.02s vs 2nd by 0.6s). In isolation `sb_z` correlates **+0.515** with the target, nearly as strong as `season_percentile`. Added to the model: `sb_z` **-0.20 (4/10)**, `gap_to_leader` **-0.37 (4/10)**, both **-0.70 (2/10)**. Decisively, **a SHUFFLED `sb_z` scored the identical -0.20** - so the real column contributes nothing over `season_percentile`. Don't rebuild these.

   **NEGATIVE 3 - and this one is informative: removing the four measured duplicates HURTS, -1.05 pts (1/10 seeds).** A lean set plus both new features was worst of all (-1.24). Provably collinear columns are not waste here: with `max_features` sampling, extra correlated copies raise the chance the mark signal is in any given split's candidate set, which acts as implicit upweighting. **So the ability signal matters MORE than the importance table suggests, and the "redundancy" is load-bearing. Do not tidy it away.**

   **Standing conclusion, now with a mechanism rather than a shrug:** the model already extracts about as much ability signal as this dataset supports. Population framing, magnitude features and de-duplication were each tested honestly and each did nothing or hurt. The two real opportunities left are **not** accuracy features: fix the head-to-head data (0o - known-wrong data feeding the 5th-largest feature), and report the metric that matches the product (Finding 1). Experiment scripts are in the session scratchpad; re-create them rather than trusting a single `--dry-run`.

    **Recommended architecture: generalise the LABEL, not the product.** Train one model on *"podium in a championship final"* pooling DL Finals + Worlds + Olympics + Europeans, rather than building a separate model per competition.     **What genuinely does NOT transfer, and is the real work:**
    - **Field selection.** DL = points standings, top N, which `run.py` mirrors exactly. Worlds/Olympics = entry standard + world ranking + a hard **max 3 per country**. Nothing in the current selection logic models a national quota. Predicting a medal from a known start list is the existing problem; predicting who is even in the field is not.
    - **Rounds.** A DL Final is one race; championships run heats → semis → final, so "will they reach the final" is a question the model has no concept of.
    - **Event coverage.** Worlds/Olympics add relays, marathon, race walks and combined events; the current 32 are individual track and field.
    - **Frequency.** Worlds biennial, Olympics quadrennial — the back-history is fine but new labels accrue far more slowly than a DL season provides.
